# ADR-001 — Redis Cache עם Fallback ל-InMemory

- **מצב:** אומץ (Accepted)
- **תאריך:** 2026-08-20
- **בעל החלטה:** RTM — Backend (.NET 8)

## החלטה (Decision)

השגת שכבת קאש באמצעות **Redis** בסגנון **Cache-Aside**, עם **Fallback שקוף
ל-InMemory** (graceful degradation): אם Redis אינו זמין, אפליקציה ממשיכה לעבוד
כרגיל על קאש זיכרון מקומי במקום ליפול.

## הקשר (Context)

ה-transaction store הראשי משלים לכל יצירת עסקה כתיבה, זמן-אמת בלוח מחוונים
(monitor) תלוי בקריאה מהירה של עסקאות. ללא קאש, כל קריאה פוגעת במאגר — תחת עומס
זמני עבודה זה מתורגם לחביון ולעומס מיותר. אולם הסתמכות **בלעדית** על Redis יוצרת
תלות חיצונית: אם השרת נופל או שהקונטיינר לא עולה, שאלת ה-availability של כל
האפליקציה נפגעת. ידרש גם הקשבה לתנאי הסביבה (למשל עבודה ללא קונטיינר).

## ההחלטה (Decision)

- קריאה חיצונית → חיפוש בקאש (Cache-Aside) → במיס → קריאת store + settlement לקאש.
- אם Redis חסר/נופל → `ICacheProvider` נעטף על-ידי `InMemoryCacheProvider` (Thread-Safe)
  עם TTL דפולטיבי, וכלול בקוד ללא שינוי של הצרכנים.
- הרשמת ה-Provider ב-DI ב-factor: מנסה חיבור אמיתי (timeout 2s), נכשל → InMemory.
- שם המפתח: prefix + key (למשל `tx:{id}`).

## השלכות (Consequences)

**יתרונות (Pros):**
- אמינות: החלטה אינה תלויה בשרת Redis אחד; מצב "אין קאש" לעולם לא משבית את
  האפליקציה — בלבד מאט קריאות.
- ביצועים: קאש מפחית עומס על המאגר וקיצר זמני תגובה בקריאות חוזרות.
- שקיפות: הצרכנים (Services/Endpoints) לא יודעים איזה Provider פעיל.

**מחיר (Cons):**
- תלות חיצונית אופציונלית (Redis) להפעלת הגדרה מלאה — נדרש ניהול קונטיינר/שרת.
- חוסר התמדה בעת fallback: נתונים ב-InMemory נאבדים עם מחזור חיים של האפליקציה.
- קומפלקסיות-ניירות: שני מימושים (Redis + InMemory) לחוזה אחד — פעם יחידה.
- Cache-Aside דורש מדיניות invalidation מסודרת כדי להימנע מ-serving stale data.
